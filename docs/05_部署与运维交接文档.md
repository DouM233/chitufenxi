## 1. 文档目的

本文说明当前系统如何运行、如何部署到网页环境、依赖哪些文件和配置、如何维护与排障，以及正式上线前必须完成的生产化改造。

本文严格区分三类内容：

- **已实现**：当前代码已经具备，可直接验证。
- **上线必做**：本地可运行，但公开部署前必须补齐。
- **推荐优化**：不阻塞单机内网上线，但影响扩展性、可观测性或长期维护成本。

接口字段见《06_HTTP接口文档》，分析口径和 Excel 输出见《07_分析方法与输出规范》。

## 2. 系统目标

系统接收一份或多份客服聊天记录，可选接收上一期正式基准报告，调用配置的 GPT/OpenAI 兼容模型完成逐条语义分析，再使用固定 Excel 母版生成正式报告。

核心原则：

1. **分析内容由本次聊天记录重新产生**，不能套用历史报告中的现成结论。
2. **有基准时继承词条和统计口径**，并计算本期与基准的差异。
3. **Excel 格式来自固定母版**，基准文件只提供历史数据，不作为输出样式模板。
4. **全部有效买家消息必须分析完成**，任何超时遗留都不能发布为正式报告。
5. **多文件代表多商品/SKU**，每个聊天文件独立分析并同时生成商品组汇总。

## 5. 运行依赖

### 5.1 推荐版本

- Windows 10/11 或 Windows Server 2022；Linux 也可运行通用链路，但专用脚本的默认路径需要全部用环境变量覆盖。
- Node.js 20 LTS。最低应为 Node.js 18，因为代码使用原生 `fetch`、`Request`、`FormData` 和 Web Streams。
- Python 3.11 至 3.14。
- Python 包：`openpyxl`。
- 可访问所配置模型服务的网络环境。
- Excel 母版文件完整存在。

## 6. 环境变量

服务按顺序读取项目根目录中的 `.env.local` 和 `.env`。如果某变量已由操作系统或进程管理器设置，文件中的值不会覆盖它。

### 6.1 必填配置

```dotenv
CHITU_LLM_API_BASE=https://your-openai-compatible-host
CHITU_LLM_API_KEY=replace-with-server-side-secret
CHITU_ANALYSIS_MODEL=gpt-5.6-sol
```

说明：

| 变量 | 必填 | 说明 |
|---|---:|---|
| `CHITU_LLM_API_BASE` | 是 | OpenAI 兼容 API 根地址。若以 `/v1` 结尾，程序追加 `/chat/completions`；否则追加 `/v1/chat/completions`。 |
| `CHITU_LLM_API_KEY` | 是 | 服务器端 Bearer Token，绝不能放入 `web/`、浏览器配置、日志或接口响应。 |
| `CHITU_ANALYSIS_MODEL` | 是 | 当前默认 `gpt-5.6-sol`，必须与上游实际支持的模型标识完全一致。 |

也兼容 `OPENAI_BASE_URL` 和 `OPENAI_API_KEY`，但生产环境建议统一使用 `CHITU_` 前缀，避免与其他服务冲突。

### 6.2 服务配置

| 变量 | 默认值 | 当前作用 |
|---|---:|---|
| `CHITU_PORT` | `8787` | Node 服务监听端口。 |
| `CHITU_MAX_ACTIVE_JOBS` | `1` | 同时运行的分析任务数；其余进入队列。 |

当前服务固定监听 `127.0.0.1`。这是适合反向代理的安全默认值；若需要容器直接暴露端口，应先把监听地址参数化，而不是临时改成公网地址后裸奔。

### 6.3 模型执行配置

| 变量 | Python 默认值 | Node 主流程实际传值 | 说明 |
|---|---:|---:|---|
| `CHITU_LLM_TIMEOUT` | `75` 秒 | `240` 秒 | 单次模型请求读取超时。 |
| `CHITU_LLM_RETRIES` | `3` | `3` | 单次请求内部重试基数。 |
| `CHITU_LLM_MAX_ATTEMPTS` | `0` | `0` | `0` 表示任务总尝试次数不设上限，以满足“一次必须全部分析”。 |
| `CHITU_LLM_WORKERS` | `3` | `6` | 分类和风险复核并发线程数。 |
| `CHITU_LLM_CACHE_DIR` | `storage/cache/llm` | 显式传入同一路径 | 已完成请求和分类块缓存目录。 |
| `CHITU_HISTORY_LOG_FILE` | 自动查找 | 未强制传入 | 指定历史 GPT/Codex 聊天记录文件，用于加载已确认分析逻辑。 |

生产建议从较保守值开始：

```dotenv
CHITU_MAX_ACTIVE_JOBS=1
CHITU_LLM_WORKERS=4
CHITU_LLM_TIMEOUT=240
CHITU_LLM_RETRIES=3
CHITU_LLM_MAX_ATTEMPTS=0
```

当前 Node 代码会覆盖部分 Python 参数为固定值。若要让运维配置完全生效，应在后续版本把这些固定值改为“环境变量优先，默认值兜底”。

### 6.4 专用脚本变量

三款卷发棒：

## 8. 网页生产部署方案

### 8.1 推荐拓扑

```text
Internet / 企业内网
  |
  v
HTTPS 反向代理（Nginx / IIS）
  |- TLS 证书
  |- 登录鉴权
  |- 上传限速和请求大小限制
  |- 访问日志与安全头
  v
127.0.0.1:8787 Node 服务
  v
Python + 模型 API + 本地持久化目录
```

异步任务创建接口会快速返回 `202`，长时间分析发生在后台，因此反向代理无需为单个 HTTP 请求设置几十分钟超时；状态查询和下载接口应保持常规超时。

### 8.2 Nginx 示例

```nginx
server {
    listen 443 ssl http2;
    server_name analysis.example.com;

    ssl_certificate     /etc/ssl/analysis/fullchain.pem;
    ssl_certificate_key /etc/ssl/analysis/privkey.pem;

    client_max_body_size 30m;

    location / {
        proxy_pass http://127.0.0.1:8787;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
    }
}
```

该示例没有包含具体鉴权实现。生产上线必须在反向代理或应用层加入企业登录、OIDC、VPN 白名单或至少 Basic Auth，不能把当前无认证服务直接暴露到公网。

### 8.3 Windows 服务化

可使用 NSSM、WinSW、任务计划程序或企业现有进程管理器。必须确保：

1. 工作目录为项目根目录。
2. Node 和虚拟环境 Python 路径可见。
3. 服务账户对项目目录及《赤兔历史分析结果》有读写权限。
4. 环境变量由安全的系统配置注入。
5. 标准输出和标准错误写入轮转日志。
6. 停止服务前先停止接收新任务并等待当前任务完成。

### 8.4 Linux systemd 示例


## 9. 当前任务模型和容量限制

### 9.1 当前行为

- 任务队列位于 Node 进程内存。
- `CHITU_MAX_ACTIVE_JOBS` 默认 `1`。
- 每个任务状态写入 `storage/jobs/{task_id}.json`。
- 上传文件在创建任务后也写入历史目录，但重试接口依赖内存中的原始 `File` 对象。
- 同一进程内超时重试会复用 LLM 缓存。
- 服务重启后，历史任务仍可查询；未完成任务会变成失败，不能原地重试。

### 9.2 不允许的部署方式

当前版本不能直接部署多个 Node 实例并使用轮询负载均衡，因为：

- 每个实例的任务 Map 和队列彼此独立。
- 状态查询可能落到另一个实例而返回 404。
- 重试所需文件对象不共享。
- 同一个 `storage/jobs` 目录并不等于共享任务调度。

### 9.3 生产扩展建议

需要多实例或重启续跑时，应改造为：

1. 上传先写对象存储或持久磁盘，数据库记录文件 ID。
2. PostgreSQL/MySQL 保存任务、进度、错误、结果和租约。
3. Redis、RabbitMQ 或数据库队列负责调度。
4. Python Worker 从持久化输入恢复任务。
5. 下载接口使用结果 ID 或短期签名 URL，不暴露服务器绝对路径。
6. Worker 幂等写入，任务可断点续跑。

## 11. 安全上线清单

当前本地版本无登录鉴权，因此以下均为上线必做：

1. API Key 只保存在服务器密钥系统或受限环境变量中。
2. 任何曾经在聊天、截图或日志中出现过的 Key，上线前必须吊销并重新生成。
3. 网页源代码和 `window.CHITU_CONFIG` 中不得出现模型密钥。
4. 通过 HTTPS 提供服务。
5. 增加用户身份认证和任务级权限校验。
6. 下载接口不能继续接受任意绝对路径作为公开参数；应改成 `task_id + artifact_type` 或签名 URL。
7. 状态响应不应向公网用户返回服务器绝对文件路径。
8. 增加扩展名、MIME、文件签名和压缩包炸弹检查。
9. 上传文件进行恶意文件扫描；宏工作簿按策略拒绝或隔离。
10. 日志中屏蔽 Key、聊天全文、订单号和个人信息。
11. 配置速率限制、并发限制、用户配额和磁盘配额。
12. 限制 CORS 来源；同域反向代理是最简单方案。

## 12. 可观测性和告警

### 12.1 当前可观察信息

- `GET /api/health`：当前运行和排队任务数。
- `GET /api/tasks/{id}`：阶段、进度、分块进度、错误和结果。
- `storage/jobs`：任务状态快照。
- `result_manifest.json`：模型调用次数、尝试次数、缓存命中、Token、完整性等。
- Node/Python 标准输出和错误：运行日志及堆栈。

### 12.2 建议监控指标

- 任务创建量、完成量、失败量。
- 排队时长、分析时长、报告生成时长。
- `active_jobs`、`queued_jobs`。
- 模型 API 成功率、超时率、429 和 5xx。
- `api_attempts`、`failed_attempts`、`cache_hits`。
- `expected_messages` 与 `analyzed_messages` 差值。
- 输入消息数、正式需求数、待复核数、风险数。
- Prompt/Completion/Total Tokens 与任务成本。
- 磁盘剩余空间和历史目录增长速度。
- Excel 生成失败、母版缺 Sheet、非法字符异常。

### 12.3 推荐告警

- 连续 3 个任务失败。
- 模型 API 15 分钟错误率超过 20%。
- 队列等待超过 30 分钟。
- 任务运行超过预设上限，例如 4 小时。
- 磁盘使用超过 80%。
- 完整性门禁失败。
- 母版哈希变化但未伴随版本发布。

## 13. 常见故障和处理

### 13.1 页面一直显示分析中

检查顺序：

1. `GET /api/health` 是否正常。
2. `GET /api/tasks/{id}` 的 `status/stage/progress`。
3. `queued_jobs` 是否持续增加。
4. Node 控制台是否有 Python 子进程错误。
5. 模型 API 是否超时、限流或返回非 JSON。
6. `storage/cache/llm` 是否持续生成缓存。

如果任务仍有进度，不应停止服务。系统目标是全量完成，长任务会比草稿分析更慢。

### 13.2 `UPSTREAM_TIMEOUT`

- 表示某次模型请求读取超时。
- 已完成分块会被缓存，同进程重试时不会全部重算。
- 当前总尝试次数默认不设上限，但网络长期不可用时任务可能长时间运行。
- 可检查 API 服务健康、并发是否过高、单块消息是否过大。
- 不得通过“把未分析消息放到待人工复核并继续发布”来规避超时。

### 13.3 `UPSTREAM_RATE_LIMIT`

- 下调 `CHITU_LLM_WORKERS`。
- 保持任务并发为 1。
- 检查账户额度和上游限流规则。
- 重试应使用原任务缓存；不要复制创建大量重复任务。

### 13.4 `SERVICE_RESTARTED`

当前版本无法恢复未完成任务。用户需要重新上传。生产化改造后，应从已落盘文件和任务数据库自动恢复。

### 13.5 模型没有扣费

可能原因：

- 命中本地 LLM 缓存。
- API Base/Key 未指向预期账户。
- 任务在进入模型阶段前失败。
- 上游代理未计费或账单延迟。

以任务 `result_manifest.json` 的 `llm_api_base`、`model`、`llm_usage.api_calls`、`cache_hits` 和 Token 为准。不要通过前端显示判断是否真实调用模型。

### 13.6 Excel 样式不一致

检查：

- 是否使用 `单品客服需求分析标准母版.xlsx` 或专用卷发棒母版。
- 母版是否被替换或损坏。
- 是否走了 `exact_excel_writer.py`。
- 动态多商品 Sheet 是从母版 Sheet 克隆，可能与专门设计的多 SKU 母版存在布局差异。
- 基准文件只提供数据，不应被当成输出样式来源。

### 13.7 Excel `IllegalCharacterError`

当前通用写入入口已清理 Excel 不允许的控制字符，并限制单元格文本到 32767 字符。如果仍出现，应确认所有写入路径都经过统一 `set_cell`，专用脚本也需要同样处理。

### 13.8 多商品被合并

上传的每个聊天记录文件应对应一个商品/SKU。检查：

- 前端是否把所有文件都以重复的 `files` 字段发送。
- `payload.files` 中每个文件是否标记为 `chat_record`。
- 文件名是否能表达 SKU，避免全部使用“聊天记录1”等通用名称。
- 有基准时，本期文件数必须与基准中的商品数一致且名称可以匹配。

## 14. 上线验收流程

### 14.1 环境验收

- Node、Python、`openpyxl` 版本正确。
- API Base、Key、模型标识配置正确。
- 两个 Excel 母版存在且可读取。
- 历史 GPT 逻辑文件可读取，或显式设置 `CHITU_HISTORY_LOG_FILE`。
- 服务账户具有输入、过程、结果、缓存和任务目录权限。
- 健康接口返回 200。

### 14.2 功能验收样本

至少准备：

1. 单聊天文件、无基准。
2. 单聊天文件、有基准。
3. 三聊天文件、无基准。
4. 四聊天文件、有多商品基准。
5. 含控制字符、链接、客服话术和系统卡片的脏数据。
6. 含售前功能咨询、售后实操、故障和风险的混合样本。

每个样本检查：

- 任务可创建、轮询、下载。
- `analysis_complete=true`。
- `expected_messages=analyzed_messages`。
- 不存在因超时而跳过的大批消息。
- 售前/售后榜按去重人数降序。
- 多文件按商品拆开。
- Excel Sheet、格式、图表和关键数字正确。
- Markdown 结论与 Excel 总览一致。

### 14.3 回归基准

将已人工确认的 Codex/GPT 正式报告作为黄金样本，但要分开验收：

- **内容一致性**：相同输入、相同模型、相同提示词和相同历史逻辑下，核心词条、阶段、人数和管理结论应接近；生成式模型不能承诺逐字一致。
- **统计一致性**：去重人数、阶段总数、排序、占比和基准变化必须精确一致。
- **格式一致性**：母版固定区域、颜色、边框、字号、宽高、合并、冻结、图表和 Sheet 顺序必须一致。

## 15. 发布和回滚

建议每次发布保留：

- 代码压缩包或 Git Commit/Tag。
- 母版文件及 SHA-256。
- 环境变量名称和非敏感值。
- 自动化测试结果。
- 三类黄金样本生成结果。
- 数据库/任务结构变更说明。

回滚时不能覆盖或删除用户上传和历史结果。代码、母版和配置应独立回滚；正在运行的任务应先排空或明确标记失败。

## 16. 当前已知限制

1. 无身份认证和用户权限。
2. 下载接口使用绝对路径参数，虽然限制在历史目录内，但不适合公网。
3. 结果接口暴露服务器绝对路径。
4. 队列和上传重试依赖单进程内存。
5. 服务重启不能自动续跑未完成任务。
6. 任务状态 JSON 不是数据库，不适合多实例并发。
7. `2449` 和 `909` 专用脚本存在，但当前网页主路由未调用；非三款卷发棒任务走通用正式分析器。
8. 前端示例配置仍保留旧 Coze 字段，真正生效的是 `service.tasksUrl`、`service.healthUrl`、`service.pollIntervalMs`。
9. 结果 Markdown 只输出核心结论，不包含 Excel 全部明细。
10. 模型输出具有非确定性；应通过统计门禁、黄金样本和抽样复核控制，而不是承诺逐字复现。

## 17. 推荐迭代顺序

### P0：公开部署前

- 身份认证、任务权限和安全下载。
- 密钥轮换与秘密管理。
- 持久化上传文件、可恢复任务和可靠队列。
- 结构化日志、告警和审计。
- 文件类型检查、病毒扫描和 PII 治理。

### P1：稳定运营

- 把历史根目录、监听地址、超时和 Worker 数全部参数化。
- 将 `2449`、`909` 等专用分析器纳入显式路由注册表。
- 提供管理员任务列表、取消、重跑、归档和费用统计。
- 加入模型请求追踪 ID 和每阶段耗时。
- 建立母版版本号、哈希和兼容性检查。

### P2：扩容与体验

- 数据库 + 分布式队列 + 独立 Worker。
- 对象存储和签名下载。
- WebSocket/SSE 推送进度，减少轮询。
- 任务估时、队列位置和历史任务页面。
- 按用户/部门配置额度与并发。
