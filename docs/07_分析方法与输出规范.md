# 赤兔客服聊天分析工作台：分析方法与输出规范

> 规范版本：V1.0  
> 对应实现：`scripts/generate_report.py`、`scripts/llm_analysis.py`、`scripts/exact_excel_writer.py`  
> 目标：让网页端和正式 Codex/GPT 分析使用同一套输入、口径、统计和 Excel 交付标准

## 1. 总原则

### 1.1 内容与格式必须分离

- **分析内容**：由模型读取本次聊天记录后重新分析产生。
- **历史基准**：只用于继承词条、定义、阶段、优先级、建议动作和历史统计，不直接复制历史结论。
- **历史 GPT 聊天记录**：作为已确认分析方法和表达规范的上下文，不作为本期数字来源。
- **Excel 母版**：只负责 Sheet、布局、颜色、字体、边框、宽高、图表和格式，不提供本期内容。

禁止行为：

- 因为文件名相同而直接返回历史报告。
- 用旧报告数字填充本期。
- 把母版中的示例数据当成真实数据。
- 接口超时后跳过消息并仍发布“正式报告”。
- 为了让网页结果看起来像 Codex 而复制旧结论。

### 1.2 正式报告完整性

正式发布必须满足：

```text
全部有效买家消息 = 全部已完成模型分类的消息
degraded_messages = 0
analysis_complete = true
```

任何消息因模型超时、解析失败或响应缺失而未完成时，任务应继续重试或整体失败，不得把数万条消息转成“待人工复核”后输出残缺报告。

### 1.3 可复现边界

统计逻辑和 Excel 格式应确定性一致；生成式语义分析不能承诺逐字一致。要获得最接近的结果，应固定：

- 相同原始输入文件。
- 相同模型标识。
- 相同历史 GPT 逻辑文件。
- 相同基准报告。
- 相同代码版本和提示词。
- 相同 Excel 母版版本。
- 相同缓存状态，或清楚标记是否复用缓存。

## 2. 分析模式

### 2.1 无基准：首次基准

输入：仅本次聊天记录。

流程：

1. 解析并过滤有效买家消息。
2. 从真实本期消息中发现完整需求词条体系。
3. 对全部有效消息逐条分类。
4. 执行售前/售后校准、风险二审和去重。
5. 形成本期统计，并把本期词条写入《上期基准》作为后续比较起点。

注意：《上期基准》在首次基准报告中实际承载的是“本期建立的基准”，Sheet 名沿用母版固定名称。

### 2.2 有基准：基准对比

输入：上一期正式基准报告 + 本次聊天记录。

流程：

1. 从基准读取词条、阶段、定义、优先级、建议动作和历史统计。
2. 优先沿用正式 V1 词条。
3. 仅当本期真实需求无法由旧词条覆盖时新增词条。
4. 逐条分析本期消息，不复制上期明细或结论。
5. 计算本期与基准的占比、日均和变化判断。

基准文件完整性要求：

- 必须能读到词条体系。
- 多商品时，本期聊天文件数必须等于基准商品数。
- 每个本期商品必须唯一匹配一个基准商品。
- 多个本期文件不能匹配同一个基准商品。

## 3. 分析器路由

### 3.1 当前网页主路由

| 任务 | 当前分析器 | 母版 |
|---|---|---|
| 同时上传 856、366、五合一三款卷发棒 | `analyze_curling_irons.py` | `三SKU首次基准_卷发棒标准模板.xlsx` |
| 其他单品或多商品 | `generate_report.py` | `单品客服需求分析标准母版.xlsx` |

### 3.2 已存在但当前未接入主路由

- `analyze_2449_bubble.py`
- `analyze_909_mirror.py`

因此，当前网页上的 2449、909 等任务实际走通用正式分析器。交接时不能宣称网页已经自动调用这些专用脚本。后续如需启用，应在 Node 端建立显式、可测试的分析器注册表。

## 4. 输入文件规范

### 4.1 聊天文件

当前通用分析支持：

- `.csv`
- `.log`
- `.txt`

建议 UTF-8 或 UTF-8 with BOM。无法解码字符会使用替换字符读取，可能影响语义判断，因此导出端应保证编码一致。

### 4.2 每个文件对应一个商品

这是多商品分析的硬规则：

```text
聊天文件数量 = 商品/SKU 数量
```

例如上传四个足浴桶日志：

```text
S-ZY-F4-5WH.log
S-ZY-F4-3BU.log
S-ZY-F4-4ABU.log
S-ZY-F4-3AWH.log
```

系统应生成四个商品的独立结果、商品组总盘、SKU 概览和每日趋势，不能把全部内容计入“未命名产品”。

### 4.3 商品名称识别

优先级：

1. 用户文字中明确的产品/商品名。
2. 已知专用任务名称。
3. 多文件共同前缀或各聊天文件名。
4. 单文件文件名。
5. 有基准且用户名称过于通用时，从基准文件名推断。

文件名会去除“聊天记录、客服聊天、raw、chat_fulltext”等后缀。建议不要使用“文件1、文件2”这类无意义名称。

## 5. 原始消息解析

### 5.1 LOG/TXT

消息头格式：

```text
发送方 2026-09-01 12:34:56
消息正文，可多行
```

会话边界：

- 包含“以下为一通会话”时开启新会话编号。
- 包含“会话结束”时结束当前消息。
- 消息头之后、下一个消息头之前的行并入同一条消息。

保留字段：

- 商品
- 会话序号
- 发送方
- 日期
- 时间
- 原文
- 源行

### 5.2 CSV

兼容字段名：

| 语义 | 可识别字段 |
|---|---|
| 买家 | `buyer`、`买家`、`客户昵称` |
| 聊天全文 | `chat_text`、`聊天内容`、`content`、`message` |
| 日期 | `chat_date`、`日期` |
| 筛选范围 | `filter_range`、`筛选范围` |
| 单条文本兜底 | `text`、`内容` |

聊天全文事件按以下顺序解析：

```text
时间
消息正文（可换行）
发送方
```

发送方等于该 CSV 行买家字段时标记为 `buyer`，否则标记为 `service`。这一步用于防止把客服回复错误计入买家需求。

如果存在筛选范围，只保留日期落在范围内的消息参与有效消息分析；原始 Sheet 仍保留可审计信息。

## 6. 文本标准化和角色过滤

### 6.1 标准化

- 删除 HTTP/HTTPS URL。
- 连续空白压缩为一个空格。
- 去除首尾空白。
- 写入 Excel 前删除不允许的控制字符。
- 单个 Excel 单元格文本最多 32767 字符。

### 6.2 客服发送方过滤

以下视为客服/系统方：

- 明确 `role=service`。
- 发送方以 `jimi_` 开头。
- 发送方名称包含“自营”或“客服”。
- 符合 `丹橘个护健康沭阳数字`、`jimi_vender_数字`、`任意名称沭阳数字` 等模式。

客服话术可进入上下文帮助判断，但不能作为买家正式需求计数。

### 6.3 纯噪声过滤

典型排除：

- 寒暄：你好、您好、在吗。
- 简短确认：好、好的、嗯、嗯嗯、OK、同意。
- 致谢：谢谢、谢谢你。
- 纯标点。
- 转人工指令。
- “没有更多内容了”。
- “请在客户端查看原始聊天记录，网页版无法展示”。
- 欢迎卡片。
- 仅有订单号/商品号的卡片。
- 无问题内容的“您选择了一个订单进行咨询”。
- 服务助手转交提示。

过滤只是得到“有效买家消息候选”，不代表每条都一定是正式需求。正式需求还必须通过模型语义门禁。

## 7. 历史 GPT 分析逻辑

系统必须读取历史 GPT/Codex 聊天记录，以继承用户已确认的分析方法和表达偏好。

读取顺序：

1. `CHITU_HISTORY_LOG_FILE` 指定文件。
2. 未指定时，在工作区根目录查找最新的 `long_text_*.txt`。

最多读取前 30000 个字符进入提示上下文。找不到历史逻辑时，当前正式链路直接失败，不允许在缺少已确认口径时冒充正式分析。

历史聊天记录的作用：

- 解释怎样判断正式需求。
- 解释售前售后边界。
- 解释词条命名风格。
- 解释管理结论风格。
- 补充特定产品口径。

历史聊天记录不是本期数据源，里面出现的数字、产品结论和旧原话不得计入本期。

## 8. 词条体系

### 8.1 V1 词条字段

每个词条至少包含：

| 字段 | 说明 |
|---|---|
| `label` | 简短、稳定、业务可读的中文词条名称。 |
| `stage` / `stages` | 默认阶段及允许阶段，可为售前、售后或双阶段。 |
| `theme` | 一级主题。 |
| `definition` | 严格定义，写清计入和不计入边界。 |
| `priority` | `P0`、`P1`、`P2`。 |
| `action` | 具体业务动作。 |
| `product_prefixes` | 可选，限制词条适用的商品/SKU。 |

### 8.2 无基准建词条

从真实本期消息中覆盖：

- 售前参数、规格、材质、配置。
- 款式、型号、适用人群和选购。
- 价格、优惠、政策、发货和购买前物流。
- 售后教程、安装、拆卸、清洗和维护。
- 实际效果、故障、退换货、少件破损和履约处理。

不允许为了“完整”硬建没有证据的类别。单产品通常建立约 12 至 24 个有效词条，多产品根据业务覆盖扩展。

### 8.3 有基准继承

- 旧词条名称、定义、阶段、优先级、动作优先沿用。
- 旧词条能覆盖时不得换一个近义新词条。
- 新词条必须说明“为什么旧词条无法覆盖”。
- 新词条写入《新增词条》和《词条与口径》。

### 8.4 命名规范

推荐：

- `款式/型号区别`
- `温度/档位/预热`
- `使用方法/教程`
- `已下单物流查询`
- `不加热/温度低`

避免：

- 过宽：`产品问题`、`售后问题`。
- 过窄：把同类表达拆成大量同义词。
- 把原因、情绪和动作混在名称中。
- 同一词条在不同期任意改名，导致基准不可比。

## 9. 正式需求门禁

### 9.1 必须计入

当前买家原话本身包含可独立统计的：

- 购买决策问题。
- 明确提问。
- 具体请求。
- 操作困难。
- 本人实际异常。
- 售后处理诉求。

### 9.2 不计入

- 纯寒暄、确认、否定、感谢。
- 只是在回答客服问题。
- 仅同步状态，没有问题或请求。
- 情绪表达但没有明确业务诉求。
- 残缺且无法独立判断的片段。
- 仅复述客服话术。
- 主题只出现在相邻上下文，当前买家原话没有提出。

### 9.3 上下文只能消歧

每条有效买家消息会附带同会话上下文：前最多 4 条、后最多 2 条。上下文角色明确标记为：

- `当前买家`
- `同买家`
- `客服`

上下文用于判断“这个、这样、还没、是的”等指代和阶段，不能把客服提出的问题强行变成买家需求。

### 9.4 一条消息多个需求

同一买家消息包含多个独立诉求时可以拆为多个正式需求。例如：

```text
这款有几个档位？送不送收纳包？今天能发货吗？
```

可分别进入温度/档位、配件/赠品、发货时效。不得为了减少数量只保留一个，也不得把同一意图拆成多个近义词条重复计数。

## 10. 售前和售后阶段判断

这是网页与人工/Codex 结果差异最大的口径之一，必须严格执行。

### 10.1 售前

以购买决策为目的，且没有明确已购或实际使用证据：

- 参数、规格、材质、尺寸、功率。
- 功能、配置、部件、耗材、赠品。
- 款式/型号区别和推荐。
- 适用人群、发质、使用预期。
- 效果原理和“是否能做到”。
- 价格、优惠、保价、正品、发票。
- 下单前预计发货/到货。
- 购买前安全顾虑。

### 10.2 售后

必须有明确已购/履约/实操/异常证据，或词条本身就是独立操作服务：

- 已下单、已购买、已收到、已拆封。
- 正在安装、充电、开机、清洗、实际使用。
- 实际效果不好。
- 故障、破损、少件、错发。
- 退款、退货、换货、维修、补发。
- 已下单后的物流查询、签收、取件和订单备注。
- “怎么用/教程/如何安装/如何换头”等具体操作教程，按售后承接压力统计。

### 10.3 双阶段词条校准

功能、配置、部件、耗材、适用性和效果原理可能同时允许售前/售后。规则：

```text
没有明确购买、收货、本人实操或实际异常证据 -> 售前
存在明确售后证据 -> 售后
词条仅允许一个阶段 -> 使用词条唯一阶段
```

不能仅因为消息中出现“怎么、如何、需要、放哪里、有什么作用”就判售后。

### 10.4 特定示例

| 买家原话/场景 | 阶段 | 理由 |
|---|---|---|
| “吸头有什么区别？” | 售前 | 功能用途咨询，无已购证据。 |
| “需要加水吗？加什么水？” | 售前 | 使用预期/配置咨询。 |
| “水箱怎么拆下来加水？” | 售后 | 明确具体操作。 |
| “冷雾有什么作用？” | 售前 | 原理和购买预期。 |
| “我收到后加了水还是不出雾” | 售后 | 已收货且实际异常。 |
| “五合一分别有哪些头？” | 售前 | 配置咨询。 |
| “这个头怎么拆下来换？” | 售后 | 具体拆装操作。 |
| “今天拍什么时候能到？” | 售前 | 下单前物流预期。 |
| “订单一直没收到，帮我查一下” | 售后 | 已下单履约处理。 |

### 10.5 阶段确定性校准

模型初判之后还会执行规则校准。对于允许双阶段、但缺少明确售后证据的功能咨询，强制归售前，以减少网页端“售后虚高”。

## 11. 分块分析和全量完成

### 11.1 消息 ID

所有商品的有效买家消息按顺序分配唯一 ID：

```text
m0000001
m0000002
...
```

### 11.2 分块

分类块按消息数和字符数控制，当前目标上限约：

- 每块最多 65 条消息。
- 每块约 14000 字符。

风险复核按候选对象再次分块，通常每块最多 40 个对象、约 14000 字符。

### 11.3 并发和超时拆分

- 多块可并发处理。
- 单块超时或结果不完整时，可进一步拆小重试。
- 已成功结果写入缓存，重试任务复用缓存。
- 对 408、409、429、500、502、503、504、网络和读取超时视为可重试。

### 11.4 完整性检查

系统记录：

- `expected_messages`
- `analyzed_messages`
- `degraded_messages`
- `analysis_complete`

只有所有有效消息都得到完整分类响应时才进入正式报告发布。

## 12. 去重与统计

### 12.1 去重键

```text
商品 + 买家 + 阶段 + 需求词条 + 当前分析周期
```

同一商品内，同一买家在同一周期多次提出同一阶段同一词条，只计 1 人次。

### 12.2 保留方式

- 首次命中作为代表明细。
- 后续同键消息写入《同人重复记录》。
- 后续原话同时拼接到首次明细的“同需求全部原话”，便于审计。
- 不同商品、不同阶段或不同词条不互相去重。

### 12.3 核心指标

设某阶段某词条去重买家数为 `count`，该阶段全部词条去重计数总和为 `stage_total`，本期有消息日期数为 `active_days`：

```text
词条人数 = unique(买家 | 商品、阶段、词条、周期)
阶段占比 = count / stage_total
日均人数 = count / active_days
原始命中 = 去重前命中该词条的消息次数
重复次数 = 原始命中中被同人同词条去重的消息条数
正式需求总数 = 去重后逐条需求明细数
```

注意：一个买家可以在多个词条各计 1 次，因此阶段正式需求数可能大于需求覆盖买家数。

### 12.4 活跃天数

`active_days` 是有效买家消息中出现的不同日期数，不是起止日期的自然日跨度。所有日均必须使用同一活跃天数口径。

### 12.5 排名

售前榜和售后榜分别排序：

```text
第一排序：同人去重人数降序
第二排序：词条名称升序
```

程序在写报告前执行排序校验；顺序错误应直接失败，不允许生成排名错乱的 Excel。

## 13. 安全和质量风险

### 13.1 两阶段识别

1. 逐条分类阶段只产生风险候选。
2. 风险候选按买家和稳定风险类别聚合。
3. 执行确定性证据门禁。
4. 再调用模型进行独立证据二审。
5. 只有确认项进入《安全质量风险》。

### 13.2 风险必须是本人实际发生

计入：

- 买家明确表示已使用/已收到后真实发生故障或伤害。
- 同一会话有明确排查后仍异常的证据。
- 原话、上下文和风险类型能够相互支持。

不计入：

- 购买前“会不会漏电/伤发”的担忧。
- 客服安全提醒。
- 教程和正常使用咨询。
- 引用评价或他人经历。
- 正常物理现象。
- 只有假设、没有本人实际发生。

### 13.3 稳定风险词汇

- 出雾故障/雾小
- 加热异常/不热
- 水箱/漏水异常
- 实际伤发/卡发/烫伤
- 实际漏电/冒烟/电气安全
- 按键/控制异常
- 疑似二手/外观异常
- 结构/配件异常
- 其他质量异常
- 普通使用或效果咨询（此类不进入正式风险）

### 13.4 856 特殊规则

856 首次询问“不出雾”只按普通售后处理。只有同会话重复出现，或明确表示已经加水、安装、擦拭、按教程排查后仍不出雾，才确认质量风险。

### 13.5 `P0风险明细` 与 `安全质量风险`

两个 Sheet 含义不同：

- `P0风险明细`：所有优先级为 P0 的需求明细，可能包括教程、退款等高优先需求，不等同于安全事故。
- `安全质量风险`：经过风险证据二审确认的安全/质量异常。

验收时不能把两个 Sheet 的数量要求为相等。

## 14. 待人工复核

只有当前消息没有形成正式需求，但模型或规则发现无法稳定判断的情况才进入复核，例如：

- 词条无法确定。
- 阶段无法稳定判断。
- 指代缺少必要上下文。
- 语义残缺但可能有需求。

禁止把“模型接口超时未分析的消息”批量放入待人工复核。接口超时属于技术失败，不是业务语义模糊。

## 15. 基准比较

### 15.1 比较指标

对售前和售后分别计算：

```text
本期人数
本期占比 = 本期词条人数 / 本期阶段总数
本期日均 = 本期词条人数 / 本期活跃天数
基准人数
基准占比
基准日均
人数变化 = 本期人数 - 基准人数
占比变化 = 本期占比 - 基准占比
日均变化率 = (本期日均 - 基准日均) / 基准日均
```

基准日均为 0 时不应直接计算无穷变化率，应按新增/未出现处理。

### 15.2 变化判断

推荐按当前实现理解：

1. 本期有、基准无：`新增词条`。
2. 基准有、本期无：`本期未出现`。
3. 占比变化绝对值达到约 3 个百分点：`结构性上升/下降`。
4. 周期不同且日均变化率绝对值达到约 20%：`日均上升/下降`。
5. 周期相同且人数不同：`人数上升/下降`。
6. 其余：`基本稳定`。

不同长度周期不能只比较总人数，必须优先看占比和日均。

## 16. 管理结论规范

输出 5 至 6 条中文结论，至少包含：

1. 数据周期、买家、正式需求和售前售后结构。
2. 售前榜首和关键售前需求。
3. 售后榜首和关键售后压力。
4. 重要风险或退款/故障问题。
5. 有基准时的重要占比和日均变化。
6. 明确可执行动作。

每条结论自然包含：

- 数据/发现。
- 业务判断。
- 具体动作。

禁止：

- 自行修改 TOP 词条名称或排名。
- 把售前和售后人数混加后再冒充某一阶段排名。
- 用自然日期跨度重算日均。
- 把有效消息率低、噪声过滤、模型过程当作经营结论。
- 使用空泛的“持续关注、加强管理”而不说明具体措施。
- 引用旧报告数字作为本期结论。

动作应落到详情页、选型对比、说明书、短视频、客服 SOP、售后排查、产品改进或质量治理。

## 22. 质量验收规范

### 22.1 数据完整性

- 原始消息数可追溯。
- 有效买家消息与《有效买家消息》行数一致。
- `expected_messages = analyzed_messages`。
- `degraded_messages = 0`。
- 每条正式需求能追溯到商品、买家、时间、源行和原话。

### 22.2 内容准确性抽检

至少抽检：

- 售前 TOP10 每词条 10 条。
- 售后 TOP10 每词条 10 条。
- 全部 P0 和安全质量风险。
- 新增词条全部样本。
- 待人工复核至少 30 条或全部。
- 多商品每个 SKU 至少 30 条。

抽检重点：

- 是否为买家而非客服。
- 当前原话是否提出正式需求。
- 词条是否最具体且不重复。
- 售前售后是否有证据。
- 风险是否本人实际发生。
- 商品归属是否正确。

### 22.3 统计验收

- 词条人数等于逐条明细中按买家去重后的数量。
- 售前和售后分别排序。
- 占比分母为本阶段需求总数。
- 日均分母为本期活跃天数。
- 基准周期不同必须检查日均变化。
- 新增词条和未出现词条判断准确。

### 22.4 格式验收

- 固定 Sheet 全部存在且顺序正确。
- 标题、色带、字体、边框、对齐和数字格式与母版一致。
- 合并单元格、行高、列宽、冻结窗格和筛选保留。
- 图表可见且数据引用正确。
- 百分比显示为百分比，不是普通小数。
- 长文本换行，不遮挡相邻区域。
- 无非法字符报错。
- 动态多商品 Sheet 名合法且不重复。
